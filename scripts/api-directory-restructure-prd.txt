# API Directory Restructure - Product Requirements Document

## Executive Summary

### Business Justification
- **Customer-Driven Need**: Customers prefer TypeScript over Python for integrations and custom development
- **Technical Debt Reduction**: Current v1/v2 versioning structure creates confusion and maintenance overhead
- **Scalability**: Enable multiple technology stacks to coexist and evolve independently
- **Team Efficiency**: Allow separate teams to work on different tech stacks without conflicts

### Project Scope
This PRD covers **Phase 1: Structural Foundation** - establishing the directory structure and moving existing code without breaking functionality. Future TypeScript implementation will be a separate effort.

### Success Criteria
- ✅ v1 FastAPI continues to work without interruption (with existing contracts)
- ✅ New directory structure supports multi-language, multi-framework development
- ✅ Shared v2 contracts foundation established with OpenAPI
- ✅ Build system (TurboRepo) updated for new structure
- ✅ Development workflow documentation updated
- ✅ Foundation ready for NestJS v2 implementation (starts at v2, no v1)

## Current State Analysis

### Existing Directory Structure
```
apps/
├── api/
│   ├── v1/                    # Python FastAPI - Production stable
│   │   ├── agents/
│   │   ├── markdown_context/
│   │   ├── a2a_protocol/
│   │   ├── core/
│   │   └── main.py
│   └── v2/                    # Python FastAPI - Development
│       ├── agents/
│       ├── markdown_context/
│       ├── a2a_protocol/
│       └── main.py
├── web/                       # Vue.js frontend
└── shared/                    # Cross-project utilities
```

### Pain Points
1. **Ambiguous Versioning**: v1/v2 doesn't indicate technology stack differences
2. **Single Language Lock-in**: Structure assumes only Python implementations
3. **Future Scaling Issues**: No clear path for adding new languages/frameworks
4. **Customer Integration Barriers**: Python requirement limits customer adoption

## Target State Architecture

### Proposed Directory Structure
```
apps/
├── api/
│   ├── shared/
│   │   └── v2/                 # Shared contracts for v2 APIs only
│   │       ├── contracts/      # OpenAPI specifications for v2
│   │       │   ├── a2a-protocol.yaml
│   │       │   ├── agent-types.yaml
│   │       │   └── common-types.yaml
│   │       ├── generated/      # Auto-generated from v2 OpenAPI
│   │       │   ├── python/     # Pydantic models for fastapi-v2
│   │       │   └── typescript/ # TypeScript interfaces for nestjs-v2
│   │       └── docs/          # v2 API documentation
│   ├── python/
│   │   ├── fastapi-v1/         # Current v1 → moved here (keeps existing contracts)
│   │   │   ├── agents/
│   │   │   ├── markdown_context/
│   │   │   ├── a2a_protocol/   # v1 contracts stay here
│   │   │   ├── core/
│   │   │   ├── main.py
│   │   │   ├── requirements.txt
│   │   │   └── Dockerfile
│   │   ├── fastapi-v2/         # Current v2 → moved here (uses shared/v2)
│   │   │   ├── agents/
│   │   │   ├── markdown_context/
│   │   │   ├── main.py
│   │   │   ├── requirements.txt
│   │   │   └── Dockerfile
│   │   └── shared/             # Python-specific utilities
│   └── typescript/
│       ├── nestjs-v2/          # Starts at v2 (uses shared/v2 contracts)
│       │   ├── src/
│       │   ├── package.json
│       │   └── Dockerfile
│       └── shared/             # TypeScript-specific utilities
├── web/                        # Vue.js frontend (enhanced for API switching)
└── shared/                     # Cross-language, cross-project utilities
```

### Technology Stack Organization & Contract Sharing
- **Language First**: `python/`, `typescript/`, `go/` (future)
- **Framework Second**: `fastapi-v1`, `fastapi-v2`, `nestjs-v2`
- **Contract Sharing**: 
  - `fastapi-v1` uses its own embedded contracts (no migration)
  - `fastapi-v2` and `nestjs-v2` both use `shared/v2/` contracts
  - Complete independence between v1 and v2 (no backward compatibility)

## Technical Implementation Plan

### Phase 1.1: Shared v2 Contracts Foundation (Week 1)
**Objective**: Establish OpenAPI v2 contract foundation for both fastapi-v2 and nestjs-v2

**Tasks**:
1. Create `apps/api/shared/v2/contracts/` directory structure
2. Extract existing v2 A2A protocol types to OpenAPI specs:
   - `a2a-protocol.yaml`: Core A2A types (Message, Task, Agent) from v2
   - `agent-types.yaml`: Agent-specific types (AgentCard, Capabilities) from v2
   - `common-types.yaml`: Shared primitives (timestamps, IDs, errors) from v2
3. Set up OpenAPI generation pipeline for v2:
   - Python: `datamodel-codegen` for Pydantic models → `shared/v2/generated/python/`
   - TypeScript: `openapi-typescript` for interfaces → `shared/v2/generated/typescript/`
4. Create generation scripts that both Python v2 and TypeScript v2 teams can use
5. **DO NOT migrate v1 contracts** - v1 keeps its existing a2a_protocol directory

**Validation**: Generated v2 types match existing Python v2 Pydantic models exactly

### Phase 1.2: Directory Structure Creation (Week 1)
**Objective**: Create new directory structure without moving code yet

**Tasks**:
1. Create new directory tree:
   ```bash
   mkdir -p apps/api/shared/v2/{contracts,generated/{python,typescript},docs}
   mkdir -p apps/api/python/{fastapi-v1,fastapi-v2,shared}
   mkdir -p apps/api/typescript/{nestjs-v2,shared}
   ```
2. Add README.md files explaining:
   - `shared/v2/`: For v2 APIs only (fastapi-v2 + nestjs-v2)
   - `python/fastapi-v1/`: Independent with own contracts
   - `typescript/nestjs-v2/`: Starts at v2, uses shared/v2
3. Create Dockerfile templates for each framework
4. Set up .gitkeep files for empty directories

**Validation**: Directory structure matches target architecture

### Phase 1.3: FastAPI v1 Migration (Week 2)
**Objective**: Move v1 to new location while maintaining all existing functionality

**Tasks**:
1. **Pre-migration preparation**:
   - Document that v1 will NOT use shared contracts
   - Ensure v1 a2a_protocol directory stays intact
   - Create migration validation checklist
2. **File migration**:
   ```bash
   # Move v1 wholesale - no contract changes
   mv apps/api/v1/* apps/api/python/fastapi-v1/
   ```
3. **Path updates only**:
   - Update import paths in moved files
   - Update any hardcoded paths to new structure
   - **DO NOT change contracts or protocol imports**
4. **Build system updates**:
   - Update TurboRepo configuration for fastapi-v1 path
   - Update package.json scripts
   - Update Docker build contexts

**Validation**: v1 API works identically to pre-migration state with zero contract changes

### Phase 1.4: FastAPI v2 Migration & Shared Contract Integration (Week 2)
**Objective**: Move v2 and integrate with shared/v2 contracts

**Tasks**:
1. **File migration**:
   ```bash
   mv apps/api/v2/* apps/api/python/fastapi-v2/
   ```
2. **Shared contract integration**:
   - Update fastapi-v2 to import from `apps/api/shared/v2/generated/python/`
   - Remove duplicate type definitions from fastapi-v2
   - Ensure all v2 types come from shared contracts
3. **Blueprint documentation**:
   - Document v2 patterns for NestJS implementation
   - Create API surface documentation for TypeScript team
   - Document business logic patterns that are framework-agnostic
4. **Build system integration**:
   - Add contract generation step to fastapi-v2 build process
   - Ensure v2 regenerates types when contracts change

**Validation**: fastapi-v2 works correctly using shared/v2 contracts

### Phase 1.5: Build System and Tooling Updates (Week 3)
**Objective**: Update all development and deployment tooling for new structure

**Tasks**:
1. **TurboRepo configuration**:
   ```json
   {
     "pipeline": {
       "build": { "dependsOn": ["^build"] },
       "test": { "dependsOn": ["build"] },
       "lint": {},
       "contracts:generate": {}
     },
     "apps": [
       "apps/api/python/fastapi-v1",
       "apps/api/python/fastapi-v2", 
       "apps/api/shared/v2",
       "apps/web"
     ]
   }
   ```
2. **Package.json script updates**:
   ```json
   {
     "scripts": {
       "api:v1:start": "cd apps/api/python/fastapi-v1 && uvicorn main:app --reload",
       "api:v2:start": "cd apps/api/python/fastapi-v2 && uvicorn main:app --reload",
       "api:v1:test": "cd apps/api/python/fastapi-v1 && python -m pytest",
       "api:v2:test": "cd apps/api/python/fastapi-v2 && python -m pytest", 
       "contracts:v2:generate": "cd apps/api/shared/v2 && npm run generate-types"
     }
   }
   ```
3. **Contract generation workflow**:
   - Set up automated regeneration when v2 contracts change
   - Create validation that Python and TypeScript get same contract updates
   - Document workflow for contract changes (coordination between teams)

**Validation**: All development commands work; contract generation produces consistent types

### Phase 1.6: Web App Preparation (Week 3)
**Objective**: Prepare frontend for API version and technology stack switching

**Tasks**:
1. **API client abstraction**:
   - Create configuration for multiple API endpoints
   - Support switching between v1-Python, v2-Python, v2-TypeScript
   - Implement API version and stack detection
2. **Configuration foundation**:
   - Environment variables for different API base URLs
   - Runtime switching capability
   - User preference persistence
3. **UI preparation**:
   - Design interface for technology stack selection
   - Plan user experience for API switching
   - Prepare for different API capabilities per stack

**Validation**: Frontend architecture ready for multi-stack, multi-version integration

### Phase 1.7: Documentation and Knowledge Transfer (Week 4)
**Objective**: Document new structure and shared contract workflow

**Tasks**:
1. **Architecture documentation**:
   - Document shared v2 contract workflow
   - Create guide for adding future technology stacks
   - Document v1 independence and v2 shared approach
2. **Team collaboration guides**:
   - Workflow for v2 contract changes (Python + TypeScript coordination)
   - Contract generation and validation procedures

3. **Developer onboarding**:
   - Updated setup instructions for new structure

**Validation**: Teams can collaborate effectively on shared v2 contracts

## Risk Mitigation

### Technical Risks
1. **Contract Synchronization**:
   - *Risk*: Python and TypeScript teams get out of sync on v2 contracts
   - *Mitigation*: Automated contract generation with validation
   - *Rollback*: Lock contract versions during critical development

2. **v1 Migration Breakage**:
   - *Risk*: Moving v1 breaks existing functionality
   - *Mitigation*: Zero contract changes for v1, only path updates
   - *Rollback*: Git branch allows clean rollback

3. **Build System Complexity**:
   - *Risk*: Contract generation adds complexity to builds
   - *Mitigation*: Incremental addition with clear documentation
   - *Rollback*: Manual contract updates as fallback

### Team Coordination Risks
1. **Contract Change Conflicts**:
   - *Risk*: Teams modify v2 contracts simultaneously
   - *Mitigation*: Clear workflow for contract change approval
   - *Rollback*: Contract versioning with rollback capability

2. **Knowledge Transfer Gaps**:
   - *Risk*: Teams don't understand shared contract workflow
   - *Mitigation*: Extensive documentation and hands-on training
   - *Rollback*: Maintain separate contracts temporarily if needed
